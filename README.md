# scpi-instrument-lab · 仪器程控小框架（C#）

用 **C#** 写的**台式仪器程控框架**：SCPI 命令编解码 → 仪器会话（查询配对 / 错误队列）→ 设备类封装（电源、DMM）→ **可复用的测量脚本**（电压扫描 + 统计 + CSV 导出），并配一套**无需真机、可复现**的自检测试。

> 这是为了补齐"**C# + 通用仪器程控**"这两个能力（芯片验证解决方案岗的明确要求）自己动手做的练习项目：
> **协议解析、会话管理、量程检查、测量脚本都是真实实现**；仪器侧用**模拟传输层**代替真机，因此**没有在真实台式仪表 / PXI 模块上验证过**（如实说明）。

## 0. 实现与验证边界（重要）

本仓库有**两套等价实现**：

| 实现 | 状态 | 说明 |
|---|---|---|
| `scpi_lab/`（Python） | ✅ **已在本机跑通**：`python -m unittest discover -s tests -v` | 简历中引用的就是这一套 |
| `src/ScpiLab` + `tests/ScpiLab.SelfTest`（C#） | ⚠️ **未编译验证** | 本机只装了 .NET **运行时**、没有 SDK（`dotnet build` 报 "No .NET SDKs were found"），因此**不声称它可用**；保留作为 C# 版本的参考实现 |

两套实现覆盖同一套语义（SCPI 解析 / 会话 / 设备类 / 测量脚本），方便对照阅读。

## 1. 构建与运行

```bash
dotnet build
dotnet run --project tests/ScpiLab.SelfTest     # 自检：输出 PASS/FAIL 与汇总
```

不依赖任何 NuGet 包（自检用自带的断言），**离线环境也能跑**。

## 2. 结构

```
src/ScpiLab/
  ScpiCommand.cs        命令解析：头 / 查询后缀 / 多参数 / 数值 + 单位前缀（k M m u n / V A Hz）
  Transport.cs          ITransport 抽象 + MockInstrumentTransport（模拟仪器，含错误队列）
  InstrumentSession.cs  会话：打开关闭、查询-响应配对、错误队列检查、超时参数
  Instruments.cs        设备类：PowerSupply（量程检查、设定与读回）、DigitalMultimeter
  Measurement.cs        SweepRunner：电压扫描 + 均值/标准差/最大偏差统计 + CSV 导出
tests/ScpiLab.SelfTest/ 自检程序（Console + 自带断言）
```

## 3. 测试覆盖

| 组 | 覆盖内容 |
|---|---|
| 命令解析 | 查询后缀 `?`、大小写不敏感、逗号多参数；单位解析 `5V` / `10mA` → 0.01 / `1.5kHz` → 1500 / `2e3` / `-2.5e-3`；非法数值与空命令 → 抛异常 |
| 会话管理 | 未打开即查询 → 抛异常；**非查询命令做查询 → 抛异常**；`*IDN?` 识别；**仪器错误码被读取并抛出而不是吞掉** |
| 设备类 | 超量程（40 V / 5 A）**在上层就被拒绝**、不下发命令；设定值读回；输出开关 |
| 测量脚本 | 0→10 V 步进 2.5 → 5 个点；平均值 / 标准差 / 最大回读偏差；注入噪声后标准差 > 0；CSV 表头与行数；起始 > 终止 → 拒绝 |

## 4. 设计决策（面试常问）

1. **为什么解析层要单独处理"单位前缀"？** 仪器手册里的参数常写成 `5V`、`10mA`、`1.5kHz`；如果只 `double.Parse`，带单位的写法直接失败，脚本可移植性很差。前缀用 `k/M/m/u/n` 映射，纯单位（V/A/Hz）不缩放。
2. **为什么查询命令必须以 `?` 结尾就报错？** 把"编程错误"和"仪器错误"分开：用写命令去查询，轻则拿到上一次的残留响应，重则阻塞到超时——**提前失败比拿到错数据安全**。
3. **为什么要读 `SYST:ERR?`？** 仪器对越界参数常常"不报错、静默接受或截断"，只看返回值会以为成功；读错误队列才能把仪器侧的问题暴露到测试报告里。
4. **量程检查放上层还是仪器层？** 两边都做：上层拒绝明显越界（避免把错误命令发下去），仪器侧错误码仍然要读（覆盖时序/状态相关的错误）。
5. **测量脚本为什么要能导出 CSV？** 测试结论必须可留痕、可被别的工具再分析；脚本化 + CSV 是"测试方法标准化、可复用"的最小形态。
6. **为什么自检不引入 xUnit/NUnit？** 现场/离线机器常常装不了包；自带断言让 `dotnet run` 一条命令就能回归，降低复现成本。

## 5. 局限（如实说明）

- **没有真机验证**：仪器侧是模拟实现；真实串口 / TCP / USBTMC / VISA 的连接、超时与并发未覆盖；
- 只实现少量 SCPI 子系统（`*IDN?` / `*RST` / `SYST:ERR?` / `SOUR:VOLT` / `SOUR:CURR` / `MEAS:*` / `SENS:FREQ` / `OUTP`），未覆盖频谱仪、网分、误码仪、数字向量仪等；
- 未做多仪器并发调度、仪器发现（`*IDN?` 扫描）与日志分级；
- 未做长时间稳定性与内存占用测试。
